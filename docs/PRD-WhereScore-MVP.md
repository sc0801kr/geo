# PRD — 공공데이터 기반 입지·공간분석 웹 (MVP)

## 0. 문서 메타
- **제품명(가칭):** WhereScore
- **문서 버전:** v1.0 (MVP)
- **작성 목적:** MVP 개발 범위/기능/지표/데이터/UX/측정/리스크를 단일 문서로 확정
- **타겟 플랫폼:** Web (모바일 우선 반응형)

---

## 1. 문제 정의 & 배경

### 1.1 사용자가 겪는 문제
- 입지분석/상권분석은 데이터 소싱(어디서?), 공간분석(어떻게?), 해석(그래서 결론은?) 단계에서 비전공자가 거의 진입 불가.
- 기존 툴은:
  - 데이터가 많지만 “결론/행동”으로 연결이 약하거나
  - UI가 전문가 중심(레이어/지표 과다)이라 포기하게 됨.

### 1.2 MVP가 해결할 것
- 주소 1개 입력만으로 **수요/경쟁/접근성/리스크/트렌드**를 요약한 한 장 리포트를 제공.
- 같은 데이터라도 A/B/C가 원하는 판단 기준이 다르므로:
  - 공통 엔진(Core Engine) +
  - **페르소나별 가중치/문장화(Interpretation Layer)**로 해석을 분리.

---

## 2. 목표(Goals) & 비목표(Non-goals)

### 2.1 목표
1. 비전공자 3분 내 결과 도달 (주소 입력 → 결론 확인)
2. 30초 내 리포트 생성(캐시 포함)
3. A/B/C 3개 모드에서 “결론 카드”가 각자 의미 있게 다르게 보이도록 설계
4. 공공데이터 기반으로 재현 가능한 점수체계 제공(상대평가 중심)

### 2.2 비목표 (MVP에서 제외)
- 실시간 유동인구 “정답” 제공(대체지표로 근사)
- AI가 매출을 확정적으로 예측(“가능성/상대점수”까지만)
- 사용자 업종을 무한 자유 입력(프리셋 기반)
- 회원 기반 CRM/리드관리(프랜차이즈 B2B 고급 기능은 후속)

---

## 3. 타겟 사용자 & 핵심 사용 시나리오

### 3.1 Persona A: 창업자(개인)
- 목표: “여기서 장사하면 망할까?”
- 행동: 후보지 1~3개 비교, 빠른 결론 원함
- 민감: 경쟁 과다, 접근성/주차, 배후수요

### 3.2 Persona B: 프랜차이즈 점포개발
- 목표: “이 상권에 이 브랜드를 여러 개 깔 수 있나?”
- 행동: 상권 규모·균질성·확장 가능성 판단
- 민감: 재현 가능성(지역 편차), 상권 크기(흡수량)

### 3.3 Persona C: 부동산 투자자(상가/주택 혼합 가능)
- 목표: “여기 가치가 오를까? 공실 위험은?”
- 행동: 성장·개발·인구구조·리스크 중심
- 민감: 변화(트렌드), 장기 리스크(침수/공사/인구감소)

---

## 4. MVP 범위 정의 (In Scope / Out of Scope)

### 4.1 In Scope (MVP)
- 주소/장소 검색 → 좌표 변환(지오코딩)
- 분석 범위: 반경 500m / 1km (기본 500m)
- 공통 지표 5종: 수요/경쟁/접근성/리스크/트렌드
- 페르소나 모드 3종: 창업 / 프랜차이즈 / 부동산
- 결과 UI: 결론 카드 + 근거 문장 + 간단 지도 레이어 + PDF/공유
- 비교 기능(초기형): 최대 3개 후보지 비교(표 형태)
- 캐시/성능: 동일 좌표·반경·모드 요청은 캐시 반환

### 4.2 Out of Scope (후속)
- 고급 공간분석(등시선/네트워크 기반 도보권)
- 유료 결제/구독(기획은 하되 MVP에는 결제 미포함 가능)
- 사용자 맞춤 업종 무한확장(세밀 업종 모델)
- “상권 추천 자동 생성” (후속 AI 추천)

## 5. UX 원칙 & 핵심 UX 플로우

### 5.1 UX 원칙(비전공자 기준)
- 입력 최소화: “주소 1개 + 모드 1개 + (옵션) 반경”
- 지표는 최대 3개를 먼저 보여주고, 나머지는 접기
- 전문용어 금지: “버퍼=도보 영향권” 등 자연어로 표기
- 모든 점수는 상대평가(백분위) + 이유 3줄로 제공

### 5.2 주요 유저 플로우

#### Flow 1: 단일 후보지 분석(핵심)
1. 홈 → 주소 입력/지도 클릭
2. 모드 선택(창업/프랜차이즈/부동산)
3. (옵션) 반경 선택(500m 기본)
4. 결과 페이지: 결론 카드 → 근거 → 지도 → 상세

#### Flow 2: 후보지 비교
1. 결과 페이지에서 “비교에 담기”
2. 비교함(최대 3개) → 비교 페이지
3. 모드 유지(모드 기준으로 비교 점수/지표 동일)

#### Flow 3: 공유/리포트
1. 결과에서 “PDF 다운로드” 또는 “링크 공유”
2. 공유 링크는 요약 카드 형태(바이럴)

## 6. 정보구조(IA) & 페이지 정의

### 6.1 IA
- `/` (홈)
- `/result` (결과)
- `/compare` (비교)
- `/about` (서비스 소개, 데이터 출처)
- `/help` (지표 설명, FAQ)

### 6.2 페이지별 목표 & 구성

#### (1) 홈(`/`)
- 목표: “주소 입력” 완료율 극대화
- 구성:
  - 상단 검색창(주소/건물명/역명)
  - 버튼: “지도에서 찍기”
  - 버튼: “내 주변(현재 위치)” (권한 요청)
  - 안내: “30초 리포트 생성 / 공공데이터 기반”

#### (2) 결과(`/result`)
- 목표: 결론을 10초 내 이해
- 구성(위→아래):
  1. 한 줄 결론(텍스트)
  2. Top 3 결론 카드(모드별 상이)
  3. 근거 3줄(Why)
  4. 지도(레이어 토글 최대 4개)
  5. 상세 섹션(아코디언 형태)
     - 수요 상세
     - 경쟁 상세
     - 접근성 상세
     - 리스크 상세
     - 트렌드 상세
  6. 액션: 비교 담기 / PDF / 공유

#### (3) 비교(`/compare`)
- 목표: 후보지 중 “1순위” 결정
- 구성:
  - 후보지 카드 3개(주소/요약)
  - Top 3 지표 비교 테이블
  - 리스크 비교(빨간 라벨)
  - 결론 추천(“목표 모드 기준 1순위”)

## 7. 기능 요구사항 (Functional Requirements)

### 7.1 공통 모듈

#### 7.1.1 지오코딩 & 위치 선택
- FR-01: 사용자는 주소/장소명 검색으로 좌표를 얻는다.
- FR-02: 지도에서 클릭한 좌표로 분석할 수 있다.
- FR-03: 현재 위치 기반 분석을 지원한다(권한 거부 시 graceful fallback).
- FR-04: 좌표가 행정구역 경계 밖/데이터 공백일 경우 오류 안내.

**UI 요구**
- 검색 자동완성
- 선택 후 “핀 고정” + 주소 표기

#### 7.1.2 분석 설정(모드/반경)
- FR-05: 모드는 3종(창업/프랜차이즈/부동산) 제공.
- FR-06: 반경은 500m(기본), 1km(옵션).
- FR-07: 모드 변경 시 결과 페이지에서 즉시 재계산/재표기.

#### 7.1.3 데이터 수집(공공데이터 API)
- FR-08: 좌표/반경 기준으로 필요한 공공데이터를 API로 호출한다.
- FR-09: API 응답 실패 시:
  - 부분 결과라도 제공(가능한 지표만)
  - “데이터 일부 누락” 배지 표시
- FR-10: 동일 요청(좌표/반경/모드)은 캐시로 재사용한다.

#### 7.1.4 점수 산출(Score Engine)
- FR-11: 모든 지표는 0~100점으로 표준화한다.
- FR-12: 점수는 “절대값”이 아니라 비교집단 대비 상대점수로 제공한다.
  - 비교집단: 같은 시/구 또는 같은 행정단위(초기: 시/군/구)
- FR-13: 점수 산출에는 최소/최대 클리핑, 이상치 처리, 결측 처리 규칙이 포함된다.
- FR-14: 최종 종합점수(모드별)는 가중합으로 계산한다.

#### 7.1.5 자연어 해석(Reason Generator)
- FR-15: 각 Top 카드마다 “근거 문장” 1~2개 생성
- FR-16: 전체 “왜 이런 결론인가요?” 섹션은 최대 3줄 요약을 제공
- FR-17: 전문 용어는 도움말(툴팁)에서만 제한적으로 사용

---

### 7.2 모드별 리포트(Interpretation Layer)

#### 7.2.1 창업 모드(A)
**Top 3 카드**
1. 수요 점수
2. 경쟁 포화도(낮을수록 좋음이므로 UI에서는 “경쟁 부담”으로 변환 가능)
3. 매출 가능성 등급(AD 또는 0~100)

**요구사항**
- FR-A1: “망할 가능성” 같은 단정 대신 “성공 가능성/주의 요인”으로 표기
- FR-A2: 경쟁은 “동종업종 수”뿐 아니라 “수요 대비 경쟁”으로 정규화
- FR-A3: 접근성은 대중교통/주차 대체지표(가능 범위) 반영
- FR-A4: “추천 한 줄”
  - 예: “이 위치는 카페보다 테이크아웃/베이커리에 유리(경쟁 대비 수요 구조상).”
  - (MVP에서는 업종 프리셋 6개 내에서만 제공)

#### 7.2.2 프랜차이즈 모드(B)
**Top 3 카드**
1. 확장 가능성(“이 상권이 여러 매장을 흡수할 수 있는가”)
2. 상권 규모(수요 총량)
3. 균질성(상권 내부 편차가 적은가)

**요구사항**
- FR-B1: “확장 가능성”은 수요 총량 + 경쟁 밀도 + 상권 편차로 계산
- FR-B2: 균질성은 반경을 4분면/격자(간단)로 쪼개 편차 계산(후술)
- FR-B3: 결과 문장에 “권장 출점 수(범위)”를 제시(정확한 숫자 단정 금지)
  - 예: “동일 포맷 기준 2~4개 점포까지는 수용 가능성이 높음”
- FR-B4: “리스크: 편차 큼”일 경우 바로 경고 배지

#### 7.2.3 부동산 모드(C)
**Top 3 카드**
1. 성장 잠재력(인구/사업체/시설 변화)
2. 임대 안정성(수요 안정 + 공실 리스크 대체)
3. 리스크(침수/공사/인구감소 등 가능한 범위)

**요구사항**
- FR-C1: 성장 잠재력은 “최근 변화율”을 강조(가능한 기간 데이터 기반)
- FR-C2: 임대 안정성은 주거·직장 기반 수요와 경쟁/공급 지표로 근사
- FR-C3: 리스크는 “강조(빨간 배지) + 근거 1줄” 필수

## 8. 지표 정의(Score Spec) — MVP 버전

원칙: 공공데이터만으로 계산 가능한 범위에서, 사용자에게는 “점수 + 이유(근거) + 상대적 위치(상위%)”로 제공한다.

### 8.1 공통 지표(5종)
1. 수요(Demand)
2. 경쟁(Competition)
3. 접근성(Accessibility)
4. 리스크(Risk)
5. 트렌드(Trend)

### 8.2 상대평가 방식
- 각 지표 raw 값을 계산 → 비교집단(예: 해당 시/구) 분포에서 백분위 → 0~100
- 결측 시:
  - 해당 지표는 “산출불가” 표시
  - 종합점수는 가능한 지표만으로 재정규화(가중치 재분배)

### 8.3 모드별 가중치(초기 제안)
- 창업: 수요 40 / 경쟁 35 / 접근성 15 / 리스크 5 / 트렌드 5
- 프랜차이즈: 수요총량(수요) 35 / 확장성(경쟁+수요) 25 / 균질성 25 / 접근성 10 / 리스크 5
- 부동산: 트렌드 35 / 수요(안정) 20 / 접근성 15 / 경쟁(공급) 10 / 리스크 20

MVP에서는 가중치는 설정 화면으로 노출하지 않고 내부 파라미터로 유지.

### 8.4 균질성 계산(프랜차이즈용, 간단 버전)
- 반경 영역을 4개 쿼드(NE/NW/SE/SW)로 분할
- 각 쿼드의 “수요 지표” 편차(표준편차/평균) 계산
- 편차가 낮을수록 균질성 점수 높음

---

## 9. 지도 & 레이어(비전공자용 제한)

### 9.1 레이어 최대 4개(토글)
- 경쟁: 동종업종 POI(점)
- 교통: 지하철/버스 정류장(점)
- 수요: 인구/가구(그리드 또는 행정동 단색)
- 리스크: 침수/공사/기타(가능 범위)

### 9.2 지도 UX 규칙
- 기본은 “결론 카드”가 상단, 지도는 그 아래
- 레이어는 기본 1개만 ON, 사용자가 확장
- 범례는 단순(좋음/보통/주의)

---

## 10. 리포트/공유 기능

### 10.1 PDF 다운로드
- FR-R1: 결과 페이지를 1장 PDF로 저장
- 포함 요소:
  - 주소/좌표/반경/모드/생성일
  - Top 3 카드 + 한 줄 결론
  - 근거 3줄
  - 지도 스냅샷(선택 레이어 반영)
  - “데이터 출처/한계” 문구

### 10.2 공유 링크
- FR-R2: 공유 링크는 요약 카드(결론+Top3) 미리보기 제공
- FR-R3: 공유 페이지에서 “원본 리포트 보기” 클릭 시 `/result`로 이동

---

## 11. 비교 기능(초기형)

### 11.1 비교함
- FR-CMP1: 결과에서 “비교에 담기”로 저장(최대 3개)
- FR-CMP2: 비교 페이지에서 제거/교체 가능

### 11.2 비교 화면
- Top3 지표를 가로 비교
- 리스크 배지를 한눈에
- “1순위 추천”은 모드 기준 종합점수가 가장 높은 후보

## 12. 온보딩/도움말(신뢰 장치)

## 13. 데이터/API 요구사항(추상화 설계)

실제 어떤 공공데이터를 쓰느냐는 나라/기관/접근권한에 따라 달라서 PRD에서는 “데이터 카테고리”와 “필수 필드” 중심으로 정의한다. (구현 단계에서 실제 API 엔드포인트 매핑)

### 13.1 필수 데이터 카테고리
1. 행정경계(시/구/동 폴리곤)
2. 인구/가구(행정동 단위 또는 격자)
3. 사업체/업종 분포(업종 코드 + 좌표 또는 집계)
4. 교통시설(정류장/역 위치)
5. 공공시설(학교/공원/관공서 등 POI)
6. (가능 시) 위험요소(침수/재난/공사)

### 13.2 공통 데이터 스키마(내부 표준)
- `location_id`, `lat`, `lon`, `address_text`
- `admin_code` (시/구/동)
- `poi`: `{type, lat, lon, category_code}`
- `stats`: `{metric_name, value, unit, as_of}`

### 13.3 API 호출 정책
- 타임아웃/재시도/레이트리밋 대응
- 캐시 키: `hash(lat,lon,radius,mode,as_of_bucket)`

## 14. 비기능 요구사항(NFR)

### 14.1 성능
- NFR-01: P95 결과 생성 30초 이내(캐시 히트 시 3초 이내 목표)
- NFR-02: 지도 렌더링 2초 이내(초기 레이어 1개만 로드)

### 14.2 신뢰/투명성
- NFR-03: 모든 결과에 “생성일/데이터 기준일(as_of)” 표시
- NFR-04: 일부 지표 결측 시, 해당 지표 비활성 + 안내 배지

### 14.3 보안/키 관리
- NFR-05: 공공데이터 API Key는 서버에서만 보관(클라이언트 노출 금지)

### 14.4 접근성
- NFR-06: 모바일 환경에서 핵심 기능 100% 사용 가능
- NFR-07: 텍스트 대비, 버튼 크기 등 기본 접근성 준수
